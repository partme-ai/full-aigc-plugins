# FigCraft main：自动保存与协作成员控制

固定main `d1d8c3f652cea20bee02bdbc3ded9a2f5362ba08`的实际原生命令目录554条，相对稳定版552条新增2项、5处契约变化，见[main差异](main-command-delta.json)。已有界面设计用例通过原生main回归；以下新增能力仅核对真实契约，尚未完成业务与宿主验收。版本字符串0.6.0不能区分这些提交，先查看当前MCP schema。

## 用户要求启用或关闭自动保存

- 当前插件通过`run_command {"command":"pref.autoSave","params":{"on":true}}`明确启用；关闭使用on:false。不要用省略on的调用当查询，也不在普通画图任务中顺便改变用户偏好。
- 先保存新工程并记录原设置，再按需求改变；检查界面设置及实际存档位置。一次设置调用成功不等于磁盘已经写入，更不证明关闭或崩溃后能恢复。
- Native桌面、浏览器存储和宿主工作区交付分别检查。结束工作仍按现有保存/重开路径交付，不用“自动保存已开”代替源文件。

## 只移除用户指定的协作成员

1. 读取`run_command {"command":"collab.peers","params":{}}`，确认当前文件、session/status、role/access及实际peers。每个打开文件有自己的会话，不把另一个标签的成员ID带来。邀请链接可能携带令牌，不写入公开记录。
2. 只在用户明确要求移除该成员、且身份具备宿主或服务器文件所有者权限时调用`collab.removePerson {client: 实际peer.id}`，保留ID返回的真实JSON类型，不按同名猜ID。例子中的“实际peer.id”是占位，必须替换。MCP包装为run_command的command/params。
3. 检查removed/name与新的peers列表，确认只移除了目标。该成员会断开但保留自己的副本；当前会话运行期间其地址不能重新加入，不代表撤销已复制的设计文件。
4. 无权限或后端不支持时保留失败结果，不用`collab.stop`停止所有人的会话来代替移除一个成员。浏览器的canHost为false，不能根据原生目录就宣称它能启动本地协作服务。

这不是自动执行的成员清理流程；没有真实协作会话与指定成员时不运行变更。对外协作和自动保存持久化仍待相应宿主/服务器验收。
